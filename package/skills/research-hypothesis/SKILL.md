# 假说构建

把研究任务、文献综述和可选知识转成若干研究候选，通过“提出者 → 批评者”的串行讨论修订，再交给“评估与格式化者”评分，由主会话排序、选择并保存结果。复现原有三角色思路，不引入额外评审角色、候选批准门禁或自动实验。

完整构建使用 Pi 的 `pi-subagents` 扩展；用户要求按本流程构建或项目指令授权委派时执行。仅询问某个假说或做局部修改时可直接完成，不因技能被加载就启动团队。被委派为其中一个角色时，只完成该角色任务并返回，不再启动本流程。

## 准备输入

先确定项目目录：用户指定目录时使用该目录，否则使用当前 Pi 会话的工作目录，并在开始时说明采用的目录。递归发现该目录及子目录中的 Markdown（`.md`、`.markdown`）和 JSON（`.json`），按内容识别任务、综述、知识、假说、约束和已有负结果；相关 JSONL 材料也可按需读取。不要求任何固定输入文件名或目录结构。

- 先列出材料路径，查看 Markdown 标题、摘要及 JSON 顶层字段，再读取所有可能有用的内容。包含项目内被 Git 忽略的研究材料；通常跳过 `.git`、依赖、缓存和工具内部运行记录，用户指定的材料优先读取。
- JSON 应解析其结构，按相关对象、数组和字段读取目标、配置、指标、资源及既有结果，保留数值单位和来源。引用时记录文件及 JSON 字段路径或数组位置；解析失败时说明错误，不能把不可读等同于没有证据。
- 材料较多时分批读取；长 Markdown 按章节、大 JSON 按对象或数组片段、JSONL 按行处理，不把路径列表、标题或截断片段当成已读全文。记录已采用的文件及位置、跳过原因和未能读取的材料，不宣称覆盖未读内容。
- 不同文件的目标、结论或状态冲突时，结合本次用户请求判断；无法确定项目范围或研究目标时先询问，不自行编造任务或创建成果。旧运行产物可以作为背景，不自动当作本次已完成的工作。

- 研究任务必须明确；已有材料可以确定目标时直接使用。缺少任务时先补齐目标。
- 缺少综述时注明“未提供文献综述”，仍可继续；可选知识缺失时省略。有 `Source Metadata Appendix` 时，传给角色的知识正文截取到该附录之前，保留原文件。
- 从本次请求和适用的项目材料中提取时间、数据、算力及技术条件，记录约束出处；用户明确更新的条件优先。区分当前有效约束、历史预算和说明性示例，后两者不自动成为本次限制。未提供的条件标为未知，估计值单独注明依据，不预设实验周期、设备或计算预算。未知条件会改变方向或可行性判断时再询问，否则保留条件性的判断与缺口。
- `max_debate_iterations` 优先使用本次请求或适用项目配置；未指定时默认 5。它是限制讨论次数的编排配置，不是实验预算。这里一轮是一次提出加一次批评，Formatter 在循环后单独执行。

主会话在项目目录的 `research/hypotheses/<run-name>/` 下建立本次成果目录；已有目录使用新名字，保留历史。写 `context.md`，包含从 Markdown/JSON 材料提取的任务、综述、可选知识、约束及其出处、未知条件、输入路径及位置、阅读范围和轮数上限。子角色只读取输入、返回结果并写指定输出，不修改共享目标与状态。

执行前阅读 [Pi 调用与上下文交接](references/pi-subagents.md)。三个角色的任务指令见 [角色提示](references/roles.md)，整理结果前阅读 [输出约定](references/output.md)。这些文件均相对本技能目录解析；研究成果写在研究项目中。

## 串行构建

主会话控制顺序、计数和收尾，开始时设置 `debate_count = 0`。三个逻辑角色使用相同模型配置，差异来自角色任务；可直接使用内置 `delegate`，不必安装同名自定义 agent。

1. **Proposer 提出或修订。** 第一轮默认给出 2–3 个方向或风险特征不同的候选；本次请求或任务需要另有数量要求时沿用。说明文献依据、科学价值与实现组成。后续轮次读取全部已有讨论，回应批评、修改候选。使用 [Proposer 提示](references/roles.md#proposer)。
2. **Critic 评审。** 收到本轮完整提案及已有讨论，检查科学价值、时间、算力、数据、技术难点、失败风险和最低成本验证方案，输出批评与结束标记。使用 [Critic 提示](references/roles.md#critic)。
3. **主会话路由。** 收到 Critic 的交接小结并读取完整评审产物后，`debate_count += 1`。评审产物包含 `READY` 且不包含 `NEEDS_REVISION`，或计数达到轮数上限时，结束辩论；否则将反馈交回 Proposer，进入下一轮。以评审产物中的标记路由，不扫描交接小结。不要按候选并行开评审，也不把 READY 解释成某个候选的独立批准。
4. **Formatter 评估与整理。** 将初始材料、实际辩论轮数和所有提案、批评交给第三个角色。它保留讨论中有价值的候选，按科学价值、创新性、可行性和验证清晰度重新评估，给出 0–1 分数并输出 JSON。使用 [Formatter 提示](references/roles.md#formatter)。此步在提前结束或用完轮数后均执行。
5. **主会话排序与保存。** 解析 Formatter 的 `ideas`，按 `score` 降序排序，默认选择索引 0，并按 [输出约定](references/output.md) 保存阶段主产物 `hypothesis.md` 及结构化配套 `hypothesis.json`。保留其他候选和讨论记录；排序选择依据是 Formatter 分数，不额外按 Critic 标记过滤。

每轮将完整提案和批评保存为 `round-01-proposer.md`、`round-01-critic.md` 等，并按轮次维护文件列表。Pi 子会话不自动获得组聊历史，主会话必须在每次任务中显式传递初始材料和此前讨论的实际路径。Formatter 也必须得到全部讨论，不能只得到最后一条评语。

每次委派还必须取得子代理的工作小结和实际产物地址，按 [子代理交接](references/pi-subagents.md#子代理交接) 由主会话单独保存为交接 JSON。主会话先读取小结，再打开对应产物继续流程；产物缺失或子任务未完成时先报告缺口，不把启动回执视为完成。Formatter 的产物 JSON 与最终交接回复分开。

这些角色基于已提供材料讨论，默认不自行检索或运行实验。用户另需补查文献时，可先按已有 `research-literature` 技能收集材料再交给角色；不得把模型推测称为已核实的新颖性、数据可得性或实测资源消耗。

## 结束与交接

向用户交付选中候选、分数与选择理由、其他候选、实际辩论轮数和成果路径。达到轮数上限同样会进入 Formatter；如仍有未解决的批评，在说明中如实保留，不把最高分等同于已验证。

需要继续方法设计时，把选中内容、依据、组成、优缺点及任务约束交给 `research-method`。仅在用户要求或已有工作流需要时继续该技能。主会话按需将选择与下一步写入项目已有的相关记录，不强制创建某个固定名称的状态文件；子角色只返回建议。
