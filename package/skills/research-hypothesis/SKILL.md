# 假说构建

把研究任务、文献综述和可选知识交给多个 Proposer 并行探索，每人提出一个假说；再通过统一 Critic 修订、Formatter 评估，由主会话排序和保存结果。保留提出、批评、整理三种职责，不增加批准门禁或自动实验。

完整构建使用 Pi 的 `pi-subagents` 扩展；用户要求按本流程构建或项目指令授权委派时执行。仅询问某个假说或做局部修改时可直接完成，不因技能被加载就启动团队。被委派为其中一个角色时，只完成该角色任务并返回，不再启动本流程。

## 准备输入

先确定项目目录：用户指定目录时使用该目录，否则使用当前 Pi 会话的工作目录，并在开始时说明采用的目录。递归发现该目录及子目录中的 Markdown（`.md`、`.markdown`）和 JSON（`.json`），按内容识别任务、综述、知识、假说、约束和已有负结果；相关 JSONL 材料也可按需读取。不要求任何固定输入文件名或目录结构。

目录约定只约束新产物，材料发现和读取仍覆盖整个项目，不限于本阶段或其他阶段目录；旧目录、用户自定义目录中的相关材料同样可用。发现相关 PDF、LaTeX、代码、数据说明或运行记录时，也按需读取，不因扩展名不同而忽略证据。

- 先列出材料路径，查看 Markdown 标题、摘要及 JSON 顶层字段，再读取所有可能有用的内容。包含项目内被 Git 忽略的研究材料；发现材料不能只依赖默认遵守 Git 忽略规则的文件列表；通常跳过 `.git`、依赖、缓存和工具内部运行记录，用户指定的材料优先读取。
- JSON 应解析其结构，按相关对象、数组和字段读取目标、配置、指标、资源及既有结果，保留数值单位和来源。引用时记录文件及 JSON 字段路径或数组位置；解析失败时说明错误，不能把不可读等同于没有证据。
- 材料较多时分批读取；长 Markdown 按章节、大 JSON 按对象或数组片段、JSONL 按行处理，不把路径列表、标题或截断片段当成已读全文。记录已采用的文件及位置、跳过原因和未能读取的材料，不宣称覆盖未读内容。
- 不同文件的目标、结论或状态冲突时，结合本次用户请求判断；无法确定项目范围或研究目标时先询问，不自行编造任务或创建成果。旧运行产物可以作为背景，不自动当作本次已完成的工作。

- 研究任务必须明确；已有材料可以确定目标时直接使用。缺少任务时先补齐目标。
- 缺少综述时注明“未提供文献综述”，仍可继续；可选知识缺失时省略。有 `Source Metadata Appendix` 时，传给角色的知识正文截取到该附录之前，保留原文件。
- 从本次请求和适用的项目材料中提取时间、数据、算力及技术条件，记录约束出处；用户明确更新的条件优先。区分当前有效约束、历史预算和说明性示例，后两者不自动成为本次限制。未提供的条件标为未知，估计值单独注明依据，不预设实验周期、设备或计算预算。未知条件会改变方向或可行性判断时再询问，否则保留条件性的判断与缺口。
- `max_debate_iterations` 优先使用本次请求或适用项目配置；未指定时默认 5。它是限制讨论次数的编排配置，不是实验预算。一轮是一批提出或修订加一次统一批评；开始时 `debate_count = 0`，Formatter 在循环后单独执行。

用户明确指定输出位置时遵循该位置；否则主会话在项目根目录下创建 `hypothese/`，本次成果目录默认即该目录。单会话与多角色版本共用这一阶段目录。已有成果时，只有明确续写才更新原目录；独立新任务使用 `hypothese/<run-name>/` 中未占用的目录，保留历史。

相对输出路径以项目根目录为基准；技能参考和脚本以本技能安装目录为基准，成果不得写入安装目录。被 `research_delegate` 委派时只在分配目录内保存本阶段产物，由主会话读取并整合到上述阶段目录；材料发现仍以运行时给出的项目根目录为准。

在本次成果目录写入阶段主产物 `hypothesis.md` 及配套文件。写 `context.md`，包含从 Markdown/JSON 材料提取的任务、综述、可选知识、约束及其出处、未知条件、输入路径及位置、阅读范围和轮数上限。子角色只读取输入、返回结果并写指定输出，不修改共享目标与状态。

执行前阅读 [Pi 调用与上下文交接](references/pi-subagents.md)。各角色的任务指令见 [角色提示](references/roles.md)，整理结果前阅读 [输出约定](references/output.md)。这些文件均相对本技能目录解析；研究成果写在研究项目中。

## 并行提出与串行收敛

主会话保留调度、比较和最终选择权。三个逻辑职责仍为 Proposer、Critic、Formatter，但 Proposer 默认拆成 2–3 个独立子代理，每个只提出一个假说。按任务指定数量或范围调整，不因为扩展上限较高就扩大团队。将人数、方向和预算记入 context；它们是本次编排约定，不是新增扩展设置。

1. **划分方向并并行提出。** 为每个 Proposer 分配稳定的 H1、H2 等标识及不同的机制、问题切面或解释角度；不预写其结论。它们读取同一任务、原始证据和资源约束，第一轮不读取同批其他提案，各自生成一个完整假说。无法合理区分方向时减少人数，避免用重复候选凑数。
2. **汇集后统一批评。** 等当前批次全部结束，读取每个工作小结及完整产物，再启动一个 Critic，比较全部假说的证据、可检验性、价值、资源与相互重叠之处。Critic 按 H1、H2 等标识给出针对性意见，末尾给出本轮整体结束标记。
3. **有界修订。** 一批提出或修订加一次完整 Critic 评审计为一轮，而非每个子代理各算一轮。完成评审后 `debate_count += 1`；评审产物包含 READY 且不包含 NEEDS_REVISION，或达到 max_debate_iterations 时进入整理。否则只把需修改的假说及相关意见交给对应 Proposer；独立修订可再次并行。保留无需改动的最新提案，Critic 仍比较全部当前候选。标识用于追踪方向，不是批准门禁。
4. **统一评估。** Formatter 读取初始材料、每个方向的最新完整假说及历次提案、批评，去重并评价科学价值、创新性、可行性和验证清晰度，给出 0–1 分数。保留候选标识和来源，不把同一方向的旧稿当作额外候选，也不为凑数量编造新假说。
5. **主会话排序与保存。** 按 Formatter 的 score 降序排序，默认选择索引 0，保存主产物 hypothesis.md 和结构化配套 hypothesis.json。选择依据仍为综合评估，不按提出者人数投票；保留替代解释和未解决批评。

单个 Critic、Formatter 使用单子代理调用；多个独立 Proposer 使用官方命名 parallel 批次。两种调用的参数必须分开，见 [调用模式与并行边界](references/pi-subagents.md#调用模式与并行边界)。后续角色必须等所需批次完成，不把批次启动回执当作结果。

每个并行子代理使用独立的工作目录和文件，例如 round-01/H1/hypothesis.md、round-01/H2/hypothesis.md；主会话先建目录。产物仍属于本次成果目录，子代理从 task 中明确的运行时项目根目录读取材料，不将自己的任务目录误当作项目根目录。后续轮次使用新目录，不覆盖旧稿。只允许主会话写阶段根目录的最终 hypothesis.md。

每名子代理先写完整产物，再返回带 role、lane_id、round、status、artifacts、summary、open_questions 的交接 JSON，主会话逐项保存并打开产物；后续角色不能只读小结。批次返回的 children 逐项处理，记录工作流及子任务 ID；一个批次成功或一个子任务完成不代表其余工作完成。

开始前估计累计调用数并为 Critic 和 Formatter 留出额度；N 个提出者、最多 K 轮时完整全量修订最多约 K×(N+1)+1 个子任务。服从运行时并发与累计配额，不修改扩展限制，不让子代理继续派生代理。配额不足时减少方向或修订轮数并说明；不能省略整理后假称阶段完成。

并行批次部分失败时保留成功方向、失败原因与覆盖缺口，不重跑整个批次。只在状态明确后对失败方向按调用协议处理；有可用候选时可继续有限范围的比较，缺失方向不计为已经探索，没有可用产物时报告受阻。设计角色默认只分析提供材料，不自行检索或运行实验。

## 结束与交接

向用户交付选中候选、分数与选择理由、其他候选、实际辩论轮数和成果路径。达到轮数上限同样会进入 Formatter；如仍有未解决的批评，在说明中如实保留，不把最高分等同于已验证。

需要继续方法设计时，把选中内容、依据、组成、优缺点及任务约束交给 `research-method`。仅在用户要求或已有工作流需要时继续该技能。主会话按需将选择与下一步写入项目已有的相关记录，不强制创建某个固定名称的状态文件；子角色只返回建议。
