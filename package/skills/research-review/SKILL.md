# 反馈评估

将成果生成与评价分开：默认由一个新会话的 Reviewer 自主发现工作目录中的相关材料，按本次任务评审已有研究成果，主会话检查交接并交付 **`review.md`**。本技能可独立使用或与其他技能自由组合，不要求先运行报告生成或任何固定前置阶段。不继承写作聊天或默认认可作者解释；不强制拆成多个评审员。被委派为 Reviewer 时直接执行评审，不再启动子代理。

完整评审使用用户已配置的 `pi-subagents`；适用项目指令或用户任务授权委派时调用。局部问答可直接完成；没有子会话能力时如实说明评审未隔离。已处于 `research_delegate` 子会话时，沿用该会话的只读工具及 `research_finish`，不要尝试启用 `subagent`。

## 准备材料

1. **自主发现材料。** 以当前 Pi 工作目录为研究项目根目录，用户明确给出其他工作目录时使用该目录。模型自行递归发现 Markdown（`.md`、`.markdown`）、JSON、相关 JSONL、PDF、LaTeX、图表和运行记录，按标题、内容与字段判断哪些有用，再读取相关内容；不要求用户指定输入文件，不预设任务、方法或结果文件名。包括被 Git 忽略的研究材料，通常跳过依赖、缓存和工具内部记录。旧评审只在复审时作为历史输入，不能预先引导首次独立判断。
2. **按实际成果确定对象。** 发现与本次评审相关的 **`report.pdf`** 时必须实际读取全文；没有该文件时，直接根据已有 Markdown、JSON、LaTeX 或其他材料确定评审对象，按内容选择 `paper` 或 `literature` 标准。PDF 不存在不是缺陷或阻塞，不要求补生成 PDF，也不自动调用其他技能。结合内容、来源清单及可用构建记录确定本次版本，不能仅按修改时间挑选。有多个无法区分的版本时再澄清。已存在但损坏或无法读取的相关 PDF 应明确报告读取障碍，不能当作不存在或声称已完成其全文检查。
3. **自主选择证据。** Reviewer 从工作目录继续发现并按需读取目标、假说、方法、结果、数据划分、指标、分析代码、原始运行/失败记录、引用原文和用户知识，不受主会话预列文件限制。相关 Markdown/JSON 按章节、字段和行号定位；大文件分批读取，记录阅读范围及未读部分。只看到摘要、路径或片段不算全文核验。作者回应属于待核验主张，不是原始证据。默认简体中文；方案或阶段报告按其自述目标评估，不要求所有成果都有自己的实验。
4. **建立输出目录。** 用户指定目录优先，否则主会话在项目 `research/reviews/<run-name>/` 建新目录，避免覆盖历史。主产物固定叫 `review.md`；辅助文件为 `context.md`、`inputs.json`、`review.json` 和必要交接记录。技能文件与脚本路径相对于本技能目录解析，成果写到研究项目，不能写进已安装技能目录。
5. **记录实际采用材料。** `context.md` 记录工作目录、本次目标、实际评审对象、读取方式、用户约束及输出位置；有相关 report.pdf 时一并记录。可附材料线索，但不是输入白名单。主会话可用下面的 `snapshot` 为实际主评审文件与本地证据记录路径和 SHA-256；这里的路径均由模型发现后填入，不是要求用户填写的输入表单。命令只记录传入文件，不替模型判断相关性，不代表已读或核验。Reviewer 在 coverage 中补充实际采用文件、读取范围与无法访问的证据；清单未登记的新增文件不在版本检查范围内。

```bash
python3 <skill-dir>/scripts/review_output.py snapshot --target <本次主评审文件绝对路径> --input-type paper --output <本次成果目录>/inputs.json
```

存在相关 report.pdf 时，从实际 PDF 获取内容：优先使用可用 PDF 读取工具；子会话缺少 PDF 能力时，主会话可从该 PDF 提取带页码的全文并按需渲染页面，放在本次成果目录供其读取，记录原 PDF 路径、指纹与读取范围。可用 Poppler 时，主会话用 `pdfinfo` 获取总页数，`pdftotext -f N -l N -layout` 逐页提取并保留页号，用 `pdftoppm` 渲染需要检查的图表页；产物写入本次成果目录，不能只提取首页或摘要。仅提供源码不算读过已存在的 PDF；其全文无法读取时交接该读取障碍，不能自报完成全部评审。全文可读但不能视觉检查时明确限制。不存在相关 report.pdf 时无需执行这些 PDF 操作，直接评审实际材料。Reviewer 可继续在工作目录发现辅助证据，不依赖主会话对成果的转述。

## 独立评审与交接

执行前阅读 [Pi 调用与交接](references/pi-subagents.md)，将 [Reviewer 提示](references/reviewer.md) 和 [输出协议](references/output.md) 的实际绝对路径交给子会话。默认一个 Reviewer、一次评审，不需要沿用旧系统的 `enable_skill`、20 条消息或七阶段编排。

Reviewer 的职责是以独立读者视角判断“这些研究成果的主张是否被证据支持，以及哪些问题需要修正”。它自主发现评审对象和辅助材料；存在相关 report.pdf 时读取其全文，没有时直接读取现有成果，再抽查决定结论的原文、方法、指标和运行记录，评价创新性、技术质量、清晰度与意义。新会话用于隔离成果生成时的聊天和既有判断，不自动保证结论正确；仍须给出可定位依据。

Reviewer 返回完整 `review.json`：摘要、优势、逐项问题、作者问题、整体评分、置信度、接收建议，以及实际检查范围和后续动作。每项问题包含位置、证据、影响与修正要求。通过 pi-subagents 调用时，另返回简短交接（完成状态、主要发现、实际成果路径和未决问题）；主会话读取完整评审并生成面向用户的 `review.md`。Reviewer 不负责改稿或执行后续实验。

每项实质问题要有稳定 ID、严重程度、位置、证据状态、影响、最小修正动作与验收条件。区分 `not_reported`（在实际阅读范围中未报告）、`unverifiable`（现有材料或工具无法核验）和 `verified`（有可定位证据支持此发现）。负结果、失败和替代解释均需公平保留；不要为凑数编造优缺点，也不要一律要求增加实验。

主会话等待真实完成结果，阅读完整 `review.json`，检查目标与输入版本、问题依据、评分及建议是否一致，再校验和生成主产物：

```bash
python3 <skill-dir>/scripts/review_output.py render --review /absolute/project/research/reviews/run-name/review.json --manifest /absolute/project/research/reviews/run-name/inputs.json --output /absolute/project/research/reviews/run-name/review.md
```

脚本使用 Python 3.10+ 标准库，无模型/API 依赖。`--manifest` 会核对登记文件是否仍与本次输入一致；不提供清单时只能检查 JSON 协议。首次生成不会覆盖已有文件；确认是本次产物更新后才用 `--force`。结构错误由主会话修复序列化问题或让同一 Reviewer 补齐，最多一次补正；不替其改变科学判断。仍不完整时保留原始输出，交付缺项说明，不把启动回执或坏 JSON 称为完成评审。

## 结束与可选复审

最终交付 **`review.md`** 的路径、主要结论、评分/置信度、建议、关键问题及核验限制。`review.json` 是生成该文档的结构化来源，人工修改评语时同步修改 JSON 并重新渲染，避免维护互相矛盾的版本。评分和接收建议只是本次模拟评审判断，不代表会议录用或研究已获验证。

默认评审结束即停止，不因低分自动改方法、重跑实验或重写报告。反馈可以要求补证、重分析、缩小结论、修正文案或停止低价值方向。可将问题建议映射到 `research-method`、`research-experiment`、`research-report`、`research-literature` 或用户决策，但仅作为后续动作。

用户要求复审时，在新目录提供修订稿、旧 `review.json` 和逐项回应，再启动新的 Reviewer。相同问题沿用原 ID，新问题从旧编号最大值之后递增，已解决问题进入 `resolved_issues` 并附本次核验依据；不能仅凭作者说已修复而关闭。正文未改变而证据补齐也可复审，记录本次新增输入。默认只复审一次，继续迭代以用户范围/预算为准，不启动无上限“修订—评审”循环。

被 `research_delegate` 委派时按 [只读交接](references/pi-subagents.md#research_delegate-只读分支) 返回完整结构化评审及 `research_finish`；`review.md` 由主会话生成，不要求无写入工具的子会话自行落盘。任务完成状态与接收建议分开：一份 Reject 评审也可以完整完成，缺少关键正文或未完成检查则交接为 partial/blocked。
