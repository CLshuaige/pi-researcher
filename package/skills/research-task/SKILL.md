# 任务解析

把用户想法细化为可以开始探索的研究任务。保留探索性与未知项，只补充下一步所需的信息。

产物正文默认跟随用户的交互语言，不以输入材料的语言决定；用户明确指定语言时遵从其要求。论文标题、代码标识符及原始记录保留原文。

先读用户最新要求、已有 task.md，并检查当前项目的 `inputs/`：网页上传的文件保存在这里，即使用户没有逐个列出文件名，也要结合这些材料理解任务。目录不存在或为空时正常继续。存在有效配置快照时使用它；否则先运行本 Skill 的 `scripts/check-settings.mjs`，读取校验后的 `.pi/research-modules.json` 设置。不要直接按未经校验的配置执行。脚本路径从 Pi 提供的 Skill 安装位置定位；配置含义见 [配置与交互](references/config-and-interaction.md)。

以当前研究项目为文件操作边界；只更新 `task.md`，按需读取本项目材料（包括 `inputs/`）、Skill 自带资源和用户明确授权的外部输入。保留上传原件，不修改、删除或直接执行上传代码。不遍历其他 Workspace 寻找资料，不修改其他阶段产物、用户级配置、凭据或服务器设置。资源不足时按交互模式处理，不操作其他项目的进程或设备。

## 交互

- `auto`：采用合理默认假设，记入 task.md；继续可做的工作。关键数据或资源缺失时说明限制，不擅自替换研究目标或生成假结果。
- `review`：只对会改变科学问题、数据、关键约束、资源或交付目标的歧义提问。每次聚焦一个决策，给出 2–4 个具体选项、推荐默认值及自定义回答入口。等待回答；用户明确选择默认值或授权自主决定后再推进依赖它的工作。
- 有 `ask_user` 时按实际工具 schema 呈现问题；否则正常对话列出选项。无交互通道时先完成独立可做的部分，交接待决问题。
- 用户追问或改变目标时先回应，再更新 task.md 及受影响的假设。

## 工作方式

1. 识别研究对象、希望回答的问题、预期产物与硬性约束。算法等尚需研究决定的事项可以保留开放。
2. 查看 `inputs/` 中实际上传的文件和相关子目录，结合用户要求读取相关数据、代码、文档与论文；材料较多时先了解清单和类型，再按相关性展开。不要只依据文件名声称已理解内容。需要解析的 PDF、图片或压缩包按实际工具能力处理；无法读取时记录具体文件与限制，不假装读过。将有用输入以 `inputs/<文件名>` 路径记入 task.md，区分已核实资源与待访问线索。
3. 涉及训练、大规模计算或专用设备时，运行本 Skill 的 `scripts/probe-environment.mjs`，读取资源与当前负载，按任务需要判断可行性；必要时再做框架检查。设备可访问不等于空闲或已分配，探测值不构成资源预留。普通轻量对话不必探测；不要因为可见多张 GPU 就安排全部使用。按需阅读 [资源判断与共享运行](references/resources.md)。
4. 仅对影响方向的未知项追问，参见 [澄清策略](references/clarification.md)。资源不足时，review 提供缩小真实验证、补充算力或先研究方法等选项；auto 继续不依赖缺失资源的部分，明确原任务的未完成项。
5. 写入 `task.md`，按需使用 [任务模板](references/task-template.md)。包括目标、必要约束、已有材料、资源可行性、预期产出和影响后续工作的假设。资源判断注明观测时间和限制，只保留影响方案的结论，不复制整份硬件清单，不把瞬时空闲量承诺为后续配额。已有文件先读后更新。
6. 用简短摘要返回目标、实质障碍和产物路径。文件中未知的事实明确写未知，不把尚未取得的科研数据或未经执行的实验视为已经存在。

task.md 记录研究需求和假设。不得将模拟、合成或演示输出描述为真实观测结果。
