# 方法设计

把研究任务、假说和可选知识转成实验方法，通过“规划者 → 批评者”的串行讨论修订，再由“评估与格式化者”综合为步骤、顺序、资源和角色分工。沿用原有三角色设计，不增加版本锁定、独立复核或执行调度机制。

完整设计使用 Pi 的 `pi-subagents` 扩展；用户要求按本流程设计或项目指令授权委派时执行。仅讨论某个对照、指标或局部修改时可直接完成。被委派为其中一个角色时，只完成该角色任务并返回，不再启动本流程。

## 准备输入

先确定项目目录：用户指定目录时使用该目录，否则使用当前 Pi 会话的工作目录，并在开始时说明采用的目录。递归发现该目录及子目录中的 Markdown（`.md`、`.markdown`）和 JSON（`.json`），按内容识别任务、假说、文献、知识、已有方案、实验结果和资源约束；相关 JSONL 材料也可按需读取。不要求任何固定输入文件名。

目录约定只约束新产物，材料发现和读取仍覆盖整个项目，不限于本阶段或其他阶段目录；旧目录、用户自定义目录中的相关材料同样可用。发现相关 PDF、LaTeX、代码、数据说明或运行记录时，也按需读取，不因扩展名不同而忽略证据。

- 先列出材料路径，查看 Markdown 标题、摘要及 JSON 顶层字段，再读取所有可能有用的内容。包含项目内被 Git 忽略的研究材料；发现材料不能只依赖默认遵守 Git 忽略规则的文件列表；通常跳过 `.git`、依赖、缓存和工具内部运行记录，用户指定的材料优先读取。
- JSON 应解析其结构，按相关对象、数组和字段读取假说、配置、数据说明、指标、资源及既有结果，保留数值单位和来源。引用时记录文件及 JSON 字段路径或数组位置；解析失败时说明错误，不能把不可读等同于没有证据。
- 材料较多时分批读取；长 Markdown 按章节、大 JSON 按对象或数组片段、JSONL 按行处理。记录采用的文件及位置、跳过原因与无法读取的材料，不把路径列表、标题或截断片段当成已读全文。
- 以本次用户请求理解目标和选择已有材料；目标或方案冲突且无法判断时先询问。不能确定项目范围或研究目标时，不自行编造任务或创建成果。旧方案与负结果可以作为背景，不等于本次已执行。

- 研究任务必须明确；已有材料能够确定目标时直接使用，缺少时先补齐。
- 假说阶段的主产物为 `hypothesis.md`，结构化配套为 `hypothesis.json`。同时从已发现的其他 Markdown/JSON 中识别相关假说或用户选定的方向，不以历史文件名限制输入。将相关内容完整传入；Markdown 含 `[SELECTED]` 时保留标记和其他候选，JSON 有 `selected_index` 等选择信息时保留并解释，由 Planner 理解，不额外要求假说 ID 或版本锁定。
- 缺少假说文件时注明 `No idea available`，仍可基于任务设计方法；用户已直接给出的假说也可作为输入。
- 可选知识缺失时省略；包含 `Source Metadata Appendix` 时，只将此前正文传给角色，保留原文件。
- 文献、知识、实验记录或既有方案对方法设计有用时一并读取和引用，不要求另建单独的综述文件。
- 从本次请求和适用项目材料中提取时间、数据、算力、工具和技术约束，记录出处；用户明确更新的条件优先。区分当前有效约束、历史预算和说明性示例，后两者不自动成为本次限制。未提供的资源条件标为未知，估计值单独注明依据，不预设实验周期、硬件或计算预算。未知条件会改变方案选择时再询问，否则保留条件性设计与缺口。
- `max_debate_iterations` 优先使用本次请求或适用项目配置；未指定时默认 5。这是讨论次数的编排配置，不是实验预算。一轮是一次规划加一次批评，Formatter 在循环后单独执行。

用户明确指定输出位置时遵循该位置；否则主会话在项目根目录下创建 `method/`，本次成果目录默认即该目录。单会话与多角色版本共用这一阶段目录。已有成果时，只有明确续写才更新原目录；独立新任务使用 `method/<run-name>/` 中未占用的目录，保留历史。

相对输出路径以项目根目录为基准；技能参考和脚本以本技能安装目录为基准，成果不得写入安装目录。被 `research_delegate` 委派时只在分配目录内保存本阶段产物，由主会话读取并整合到上述阶段目录；材料发现仍以运行时给出的项目根目录为准。

在本次成果目录写入阶段主产物 `method.md` 及配套文件。写 `context.md`，包含从 Markdown/JSON 材料提取的任务、完整假说、相关背景、资源约束及其出处、未知条件、输入路径及位置、阅读范围和轮数上限。子角色只读取材料、返回方法设计并写指定输出，不修改共享状态、实现代码或运行实验。

执行前阅读 [Pi 调用与交接](references/pi-subagents.md)。角色任务见 [角色提示](references/roles.md)，Formatter 调用和收尾前阅读 [输出与执行交接](references/output.md)。技能参考文件相对本技能目录解析，成果写在研究项目中。

## 串行设计

主会话控制顺序和计数，开始时设置 `debate_count = 0`。三个逻辑角色使用相同模型配置，通过角色任务区分；均可使用内置 `delegate`，无需新增同名自定义 agent。

本技能由主会话逐次调度，每次 `subagent` 只启动当前一个角色，使用 `agent` 与 `task`。不传 `workflow`、`args` 或 `options.script`，也不以 `workflow: false` 关闭工作流；整个辩论流程不等于工具的 workflow 调用模式。管理查询另用 `action`，不与角色启动合并。参数互斥与校验报错的恢复见 [单角色调用边界](references/pi-subagents.md#单角色调用边界)。

1. **Planner 规划或修订。** 阅读任务、完整假说与知识，设计能支持或否定假说的实验，说明基线、对照、测量、步骤、依赖和结果解释。先保证科学有效性，后续根据批评调整成本和范围。使用 [Planner 提示](references/roles.md#planner)。
2. **Critic 评审。** 阅读本轮完整方案和已有讨论，检查步骤清晰度、工具和资源可得性、技术困难、失败风险及科学有效性，给出修改建议和结束标记。使用 [Critic 提示](references/roles.md#critic)。
3. **主会话路由。** 收到 Critic 的交接小结并读取完整评审产物后，`debate_count += 1`。评审产物包含 `READY` 且不包含 `NEEDS_REVISION`，或达到轮数上限时，结束辩论；否则将批评交回 Planner，开始下一轮。以评审产物中的标记路由，不扫描交接小结。不按实验并行规划。
4. **Formatter 综合与格式化。** 将初始材料、全部规划与批评、实际轮数交给第三个角色。它综合 Planner 设计与 Critic 的简化建议，输出完整方法 JSON；允许在综合中调整方案，不另加一轮最终评审或候选评分。使用 [Formatter 提示](references/roles.md#formatter)。提前结束或达到轮数上限后均执行此步。
5. **主会话保存方法。** 读取 Formatter JSON，生成阶段主产物 `method.md` 及结构化配套 `method.json`，字段和文档内容遵循 [输出约定](references/output.md)。保留原始输出及全部讨论，不把方法设计完成称为实验完成。

每轮保存 `round-01-planner.md`、`round-01-critic.md` 等完整输出。每次调用显式给出 `context.md` 及此前全部讨论的实际路径，用文件交接提供原组聊中的共享上下文。Formatter 同样需要全部规划与批评，不能只得到最后一条意见。

每次委派还必须取得子代理的工作小结和实际产物地址，按 [子代理交接](references/pi-subagents.md#子代理交接) 由主会话单独保存为交接 JSON。主会话先读取小结，再打开对应产物继续流程；缺少产物或子任务未完成时先报告缺口，不把启动回执视为完成。Formatter 的方法 JSON 与最终交接回复分开。

设计角色默认分析给定材料，不自行检索、实现或测试方案。缺少资源信息时写明假设与缺口，不把工具可得性、预计运行时间或资源估计说成已经验证。需要另行核查时，由主会话按用户需要补充材料。

## 结束与下游交接

交付方法概述、步骤与顺序、Engineer/RA 分工、资源、关键批评、实际轮数、结束原因和成果路径。轮数耗尽也进入 Formatter；尚未解决的意见如实保留，不额外引入批准状态。

Engineer 表示代码、数据处理、分析、自动化和技术验证；RA 表示需要真人参与的标注、访谈、主观评估或手工实验。它们是方法产出的执行角色，不是此处要启动的子代理，也不代表已有对应人员或任务已经完成。

用户要求继续实验时，将 `method.md` 及相关输入交给 `research-experiment`。使用 engine 时，按 [engine 接入](../../docs/engine.md) 在分配的实验目录准备 `method.md`，说明文件边界、环境、运行方式、验收证据和停止条件；已有环境适用时复用。设计阶段不自动调用 `engine_start`，不代替真人完成 RA 步骤。主会话按需将方法与下一步写入项目已有的相关记录，不强制创建固定名称的状态文件。
